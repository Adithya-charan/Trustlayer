# B1: Smart Data Masking System for PII Protection

This is the B1 implementation inside TrustLayer. It is a database-agnostic engine that **discovers sensitive columns automatically** and **masks values at
query time according to the caller's role**, without ever changing the stored data. It works on the organizer's synthetic *Saffron Bank* dataset
(9 tables, 129,260 rows) in **Neon PostgreSQL**, the only supported backend.

> All data is synthetic. This is a prototype for a hackathon, not a compliance certification. Never call or message any phone number in the dataset.

## 1. What it does

| Requirement (problem statement) | Where it lives |
|---|---|
| Scan schema metadata and row samples; auto-tag PII fields (`PII_HIGH`, `FINANCIAL_CONFIDENTIAL`, ...) | `backend/app/b1/detect.py`, `discover.py` |
| Database abstraction compatible with at least two backends | `backend/app/b1/targets.py`: **Neon PostgreSQL** and the organizer's **SQLite** file are connected and verified read-only; **MySQL** is implemented (`B1_MYSQL_URL`, PyMySQL, read-only session) but **not verified against a live server** and shows "not configured" until a URL is set. Each backend's state in the UI comes from a live health check |
| Dynamic masking at query time by role (Admin full, Support partial like `4111-XXXX-XXXX-1111`, Analyst redaction or hashes) | `backend/app/b1/mask.py`, `query.py` |
| Interactive demonstration where roles can be compared; underlying tables intact | UI page **Access Policies** (same query, each role side by side; `frontend/src/pages/Policies.jsx`), plus Discovery, Data Explorer, Users & Access and Audit Center; API under `/api/b1/*` |

## 2. Architecture and data flow

```
 browser (React app)  ──►  FastAPI /api/b1/*  ──►  role from the signed JWT (never from the request)
                                   │
        ┌──────────────────────────┼───────────────────────────────────────┐
        ▼                          ▼                                       ▼
  discover.py (Admin)        query.py                                 audit (existing)
  inspector + bounded        1. parse/validate request (structured     field NAMES, kinds,
  random sample per column      or one sqlglot-validated SELECT)        strategies, decision;
  detect.py classifies:      2. allow-list table/columns vs the         never values
  name rules + value            reflected schema; values are bound
  patterns (+ Luhn) +           parameters
  free-text scan             3. read-only DB connection fetches rows
  stores TAGS ONLY in        4. mask.py applies the role's strategy to
  b1_field_tags                 each returned cell (stored data untouched)
        │                          │
        ▼                          ▼
   targets.py  ── Neon PostgreSQL, schema `saffron_bank` (READ ONLY transactions; health check asks `transaction_read_only`)
```

* **Separation of concerns:** connections/metadata (`targets.py`), classification (`detect.py`), persistence of tags (`discover.py`), policy and masking
  (`mask.py`), query validation and execution (`query.py`), HTTP and error mapping (`api/b1.py`).
* **Dialect differences** (identifier quoting such as the upper-case `cards` columns, random sampling, schema scoping, read-only mode) are handled in
  `targets.py` and SQLAlchemy; the rest of the engine is backend-neutral.

## 4. Dataset preparation and import
The organizer pack (not stored in this repository) provides CSV files, a ready SQLite database and PostgreSQL/MySQL scripts. `README.md` of the pack
describes the tables. Never edit the pack files.

**SQLite:** no longer used by the application. Any local copy of `saffron_bank.db` is left in place and ignored.

**PostgreSQL (Neon):** the organizer's PostgreSQL schema starts with `DROP TABLE IF EXISTS "customers"`, and TrustLayer's own tables (`public.customers`,
`public.users`, ...) live in the same database. Running the pack as-is would destroy them, so use the safe loader, which creates a **separate schema**:

```bash
cd backend
python -m scripts.load_saffron_pg --schema-file "<pack>/sql/postgres/01_schema.sql" --data-file "<pack>/sql/postgres/02_data.sql" --dry-run   # validate only
python -m scripts.load_saffron_pg --schema-file "<pack>/sql/postgres/01_schema.sql" --data-file "<pack>/sql/postgres/02_data.sql"
```
The loader never touches `public`, accepts only the expected `CREATE`/`INSERT` statements for the nine tables, refuses to run if the schema already
has tables (no duplicate imports), checks every row count against the organizer's published counts, and rolls back on any mismatch.

**Migration and users:**
```bash
cd backend
alembic upgrade head                                                     # adds ONE table: b1_field_tags (additive)
python -m scripts.seed_b1 --users-csv "<pack>/data/users.csv"            # the 9 sample users (Admin/Support/Analyst); password = DEMO_PASSWORD
```

## 7. PII detection
Per column the scanner combines: **column-name rules** (abbreviation aware: `cust_nm`, `mob_no`, `pita_nm` = father's name), **value patterns** on a bounded random
sample (PAN, Aadhaar-style 12 digits, SSN formats, e-mail, phone, **Luhn check for card numbers**), and a **free-text scan** for identifiers embedded in
long text. Output per column: `kind`, `tag`, `confidence`, `status`, `methods`, `match ratio`, a short rationale.

* Tags: `PII_HIGH` (PAN, Aadhaar, SSN, card numbers, free text containing identifiers), `PII_MEDIUM` (names, phones, e-mail, DOB, addresses, postal codes),
  `FINANCIAL_CONFIDENTIAL` (account numbers, balances, amounts, limits, card expiry, transaction references), `NON_SENSITIVE`.
* **Confirmed** (confidence >= 0.8) vs **uncertain** (0.5-0.8, needs review) vs untagged. Examples of deliberate uncertainty: branch phone/e-mail (organisation
  contact data), postal codes, name-only evidence on an empty column, and columns where the name and the values disagree.
* **Hidden PII is found by values:** `loan_applications.col_7` has a meaningless name but holds PANs; it is tagged `PII_HIGH` from its values alone.
* Admins can **review and correct** a classification (`PATCH /api/b1/fields`); reviewed columns survive re-scans. Only tags/confidence/methods are stored; sampled
  values stay in memory and never reach logs, audit records or responses.
* Nulls, empty columns, binary columns and odd value types are handled without guessing (an empty column is never "confirmed").
* No LLM, no RAG. Presidio (used elsewhere in TrustLayer) is not used by this module.

## 8. Masking policy
| Role | Behaviour |
|---|---|
| **Admin** | real values for everything |
| **Support** | partial masks: cards `4111-XXXX-XXXX-1111`, PAN/Aadhaar/SSN/phone/account keep the last 4, e-mail `a***@domain`, names `A**** R**`, DOB year only, address keeps the last segment, amounts as bands (`10,000-99,999`), identifiers embedded in free text masked in place |
| **Analyst** | PAN, card, account and reference numbers are **keyed hashes** (stable, joinable, not reversible); names, contacts, DOB, addresses, amounts and free text are **redacted**; **Aadhaar and SSN columns are withheld entirely** |
| any other account role | **refused (403)**; unknown roles never default to a more permissive role |

Unclassified columns are treated as sensitive. `NULL` stays `NULL`. Non-admin roles **cannot filter or sort on sensitive columns** (that would confirm or rank
masked values). The policy is shown in the UI and at `GET /api/b1/policy`. Built-in defaults live in code (`mask.py`); an Admin can override a role's or a single user's strategy per kind of data
(`PUT /api/b1/policy/overrides`, stored in `b1_role_policies` / `b1_user_policies`). Resolution is user override, then role override, then default. Admin accounts can never be
restricted and non-sensitive columns are never masked. Each change is audited with old and new strategy and applies to that user's very next query.

## 9. Authentication and roles
JWT bearer tokens (existing TrustLayer auth, bcrypt password hashes). The role comes only from the token; request bodies that try to supply a role are rejected
(`extra` fields forbidden). Permissions: `b1_query` (Admin, Support, Analyst), `b1_scan` / `b1_review` / `b1_compare` (Admin). `security_admin` acts as Admin and
`analyst` as Analyst. Users cannot change their own role through any B1 endpoint.

## 10. API
All endpoints need `Authorization: Bearer <token>` (get one from `POST /api/auth/login`).
```
GET  /api/b1/targets                     connection status per backend (no credentials)
POST /api/b1/scan            {target}    Admin: discover and tag
GET  /api/b1/schema?target=              tables, columns, tags
GET  /api/b1/fields?target=&status=      classifications (confirmed / uncertain / none)
PATCH /api/b1/fields {target,table,column,kind}   Admin: review a classification
GET  /api/b1/policy                      role x kind strategy matrix (with Admin overrides)
GET  /api/b1/policy/overrides            Admin: edited policies
PUT  /api/b1/policy/overrides            Admin: {scope: role|user, subject, kind, strategy}; audited old -> new
POST /api/b1/policy/overrides/reset      Admin: back to the built-in policy
GET  /api/b1/policy/users/{username}     Admin: the strategy this user effectively gets per kind
GET  /api/b1/users                       Admin: the demo users with role and last activity
GET  /api/b1/overview                    real counts for the Overview page (tables, fields, audit totals)
POST /api/b1/preview {target, sql, username}   Admin: the same query exactly as that user would receive it (no impersonation, audited)
POST /api/voice-command {text}           one spoken/typed command -> one approved intent (see DEMO.md); policy changes return a signed confirmation
POST /api/voice-command/confirm {token}  redeems that confirmation for the same signed-in user only
POST /api/b1/query    {target, sql}  or  {target, table, columns, filters, order_by, limit}     masked for the caller's role
POST /api/b1/compare  {same body}        Admin: the same rows for every role + source fingerprint before/after
GET  /api/b1/audit                       Admin: recent B1 events (field names and strategies only)
```
`sql` accepts one `SELECT` on one table (columns or `*`, AND-ed comparisons against literals, one `ORDER BY`, `LIMIT <= 100`). Joins, aggregates, sub-queries,
`OR`, `LIKE`, functions, comments-as-code and multiple statements are rejected. The query is parsed with sqlglot into a structured request; the original text is never executed.

## 12. Security considerations
Read-only connections (READ ONLY transactions on Neon); allow-listed identifiers and bound parameters; server-side role enforcement; fail-closed defaults; no values in logs, audit
records or error messages; rate limiting (60 queries/min per user); secrets only in `backend/.env` (git-ignored). See the tests under "bypass, injection, validation"
and "data integrity" in `tests/test_b1_api.py`.

## 13. Known limitations
* Only Neon PostgreSQL is supported (SQLite was removed on request), so the brief's "at least two backends" requirement is not met. MySQL is not implemented.
* Policies are code-defined; they cannot be edited at runtime.
* No joins or aggregates (they would need their own masking rules); the demo reads one table at a time.
* Detection is rule/pattern based and English/Indian-format oriented; names in the *values* are weak evidence, so name columns rely mostly on column names.
* The in-memory rate limiter and the "source fingerprint" (row count + hash of the first 200 rows by primary key) are prototype-grade.
* Hashing key is derived from `JWT_SECRET`; rotating that secret changes all hashes.
